# 03 – Database Design

Engine: **PostgreSQL 16** (SQLAlchemy 2 ORM). Tables are created automatically on application start
(`Base.metadata.create_all`). ER diagram: [diagrams/er_diagram.md](diagrams/er_diagram.md).

## Entities (required set → table)
| Required entity | Table |
|---|---|
| Users (citizens, CMO admins, officers) | `users` (`role` column) |
| Departments | `departments` |
| Grievances | `grievances` |
| Grievance History | `grievance_history` |
| Department Assignments | `department_assignments` |
| Attachments | `attachments` |
| Citizen Feedback | `citizen_feedback` |
| Contact Enquiries | `contact_enquiries` |

## Tables
### departments
`id` PK · `code` unique · `name` unique · `description` · `default_category`.

### users
`id` PK · `name` · `email` unique (stored lower-case) · `mobile` · `password_hash` (bcrypt) · `role` (`citizen|cmo|officer`) ·
`department_id` FK→departments (officers only) · `is_active` · `created_at`.

### grievances
`id` PK · `reference_no` unique (`KGR-<year>-<6-digit id>`) · `citizen_id` FK→users · `district` · `category` · `subject` ·
`description` · `priority` · `status` · `department_id` FK (current) · `assigned_officer_id` FK · `due_date` · `escalated`,
`escalated_at` · `report_text`, `report_status` (`Pending CMO Review|Accepted|Rejected`), `report_submitted_at` ·
AI advisory fields: `ai_department_id` FK, `ai_category`, `ai_priority`, `ai_summary`, `ai_provider`, `ai_is_fallback`,
`ai_duplicates` (JSON), `ai_reviewed`, `ai_reviewed_by` FK, `ai_reviewed_at` · `created_at`, `updated_at`, `resolved_at`.
Indexes: `reference_no`, `citizen_id`, `district`, `category`, `priority`, `status`, `department_id`, `created_at`.

### grievance_history (append-only)
`id` PK · `grievance_id` FK · `action` · `from_status` · `to_status` · `remarks` · `visibility` (`public|department|internal`) ·
`actor_id` FK→users · `actor_role` · `created_at`. Every status change and significant action (submit, forward, triage,
escalate, remark, report submitted/accepted/returned, feedback, reopen) writes a row.

### department_assignments
`id` PK · `grievance_id` FK · `department_id` FK · `officer_id` FK (nullable) · `assigned_by` FK→users · `note` · `is_active` ·
`assigned_at`. Previous rows are set inactive on reassignment, preserving the routing history.

### attachments
`id` PK · `grievance_id` FK · `kind` (`complaint|action_report`) · `filename` (sanitised) · `content_type` · `size` ·
`data` BYTEA (lazy-loaded) · `uploaded_by` FK · `uploaded_at`.

### citizen_feedback
`id` PK · `grievance_id` FK · `citizen_id` FK · `rating` 1–5 · `comment` · `created_at`. One feedback per resolution cycle
(a reopened-then-resolved grievance can be rated again).

### contact_enquiries
`id` PK · `name` · `email` · `subject` · `message` · `created_at`.

## Relationships
- department 1 — N users (officers)
- user (citizen) 1 — N grievances; department 1 — N grievances; user (officer) 1 — N grievances (assigned)
- grievance 1 — N history / assignments / attachments / feedback

## Integrity & design notes
- Enumerations (status, priority, category, district) are validated in the API layer; categories/districts are reference lists
  in code, easy to move to lookup tables if they need admin editing.
- `grievances.status` is the denormalised current state; `grievance_history` is the source of truth for the trail.
- Passwords are never stored in clear text. Attachment bytes are excluded from list queries (deferred column).
- Demo data is generated by `app/seed.py` (fictional; deterministic random seed).
- Production recommendations: Alembic migrations, DB-level CHECK constraints for enums, automated backups/PITR, read replica for reporting.
